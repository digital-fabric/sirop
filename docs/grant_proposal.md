## Project title

### Sirop: General-Purpose Macro-like Code Generation for Ruby

## Project details

Ruby is a programming language famous for its metaprogramming facilities. DSLs
are ubiquitous to Ruby code and have been one of the main drivers behind the
popularity of Ruby on Rails and other Ruby-based frameworks and tools. Those
DSLs frequently use techniques such as `instance_eval` or `method_missing` for
dynamically generating code or implementing dynamic behaviour. But these
techniques introduce a significant performance overhead, both in terms of
increased allocations (and therefore GC pressure), and slower code execution.

Another technique for dynamic code generation is by `eval`ing an interpolated
string. This technique is used notably by the `erb` gem, which "compiles" an ERB
template into optimized Ruby code. Using that technique we can achieve optimal
performance, but interpolating strings that contain Ruby source code can be
error-prone and complex and may also lead to code-injection vulnerabilities.

Many Ruby gems use the technique of `eval`ing dynamically constructed strings
with Ruby source code snippets, including Rails, Sequel, HAML, Roda, Memoist and
Phlex, among others. In my own projects I've implemented dynamic code-generation
using this technique in order to achieve optimal performance, or *machine
happiness* without sacrificing *developer happiness*. In
[Papercraft](https://github.com/digital-fabric/papercraft), a DSL for writing
HTML templates using plain Ruby is [compiled into optimal
code](https://github.com/digital-fabric/papercraft/blob/master/lib/papercraft/compiler.rb)
using string interpolation (just like ERB). In
[Syntropy](https://github.com/digital-fabric/syntropy), file-based routing is
implemented by compiling a nested directory hierarchy into [optimized Ruby
code](https://github.com/digital-fabric/syntropy/blob/a0a30043b0712b902037be5f1f8b769f705711d3/lib/syntropy/routing_tree.rb#L448).
In both cases, the "compiled" source code is generated by interpolating and
concatenating strings.

The goal for this grant proposal is to make Ruby code generation easier and
safer by introducing a flexible mechanism for transforming lambdas or methods
into AST, manipulating the AST and transforming the AST back to a lambda or
proc, thus allowing developers to implement DSLs without compromising on
performance.

More specifically, the aim for this grant proposal is to introduce a
general-purpose `quote`/`unquote` facility for dynamically generating code
similar to what's available in other programming languages such as Lisp (where
this technique was first introduced), Elixir, Julia etc.

With `#quote` (convert code to AST), `#unquote` (convert a Ruby object to AST),
and `#to_source` (convert AST to source code), we could convert arbitrary data
structures to Ruby code, and dynamically generate optimized code for a variety
of use-cases, which may include compiling templates, providing debugging
facilities, or as discussed above, implementing DSLs without paying a
performance tax.

As an example of how such a mechanism may be used, here's how we may implement a
general-purpose validation facility that generates a lambda that validates a
value against one or more conditions, using different techniques:

```ruby
# Usage:
validate_foo = make_validator(String, /foo/)
validate_foo.('foobar') #=> true
validate_foo.('barbaz') #=> RuntimeError!

# inline lambda generation
def make_validator(*conds)
  ->(v) {
    conds.each { raise unless it === v }
    true
  }
end

# eval with string interpolation
def make_validator(*conds)
  eval([
    "->(v) { ",
    *(conds.map { "raise unless (#{it.inspect}) === v;" }),
    "true }"
  ].join)
end

# eval with the proposed quote/unquote mechanism
def make_validator(*conds)
  ast = quote {
    ->(v) {
      unquote(conds.map) { |c|
        quote { unquote(c) === v }
      }
      true
    }
  }
  eval(ast.to_source)
end
```

While the inline lambda generation works just fine, it is significantly slower
(about 1.65x) than the both the string interpolation and the quote/unquote
implementations. The string interpolation implementation requires careful
handling and assembly of the different parts of the generated code, and may also
lead to subtle bugs if used incorrectly by the developer, since it uses
`#inspect`. The quote/unquote implementation generates code that is just as fast
as the string interpolation implementation, but is more flexible. For example,
it correctly handle a lambda condition, e.g. `make_validator(->(x) { x > 42 })`,
since the given lambda will be correctly converted to AST (using `unquote`).

This project will enhance the capabilities of
[Sirop](https://github.com/digital-fabric/sirop), which is an existing Ruby gem
that can already return an AST generated using Prism for a given lambda or
method at runtime, and can transform such an AST back to source code.

## Project deliverables

My proposal aims to work on the following objectives:

- Implement a general-purpose way for Sirop to transform a *synthetic* AST into
  source code, and generate lambdas and methods.
- Implement `quote` / `unquote` for generating and manipulating synthetic ASTs.
- Create a comprehensive suite of test cases for this functionality.
- Put the technique into practice by integrating it into gems such as Papercraft
  and Syntropy.
- Provide alternative implementations using `quote`/`unquote` for gems that use
  `eval` along with interpolated strings for performance, such as Roda, Memoist.
- Explore the implications and limitations of this technique. Compare the
  performance characteristics of this technique vs traditional approaches to
  metaprogramming.
- Accompany the code with comprehensive documentation.
